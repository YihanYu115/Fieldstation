# Role usage

[English documentation](README.md) · [Chinese original](../../orchestration/ROLE_USAGE.md)

A Queue publisher selects an experimenter profile. First use an authorized Host catalog to inspect its responsibilities and configuration options. Catalog visibility grants neither launch nor IM permissions; the target Host independently checks before claiming. Other roles can still be activated by trusted scripts using Board or Inbox.

These tools are capabilities to use as needed, not a mandatory per-session sequence. Actual permissions are determined by services and host bindings. An example project may hand a new research question directly to a scientist, who passes guidance to a manager to arrange work. The example scheduler prioritizes pending Inbox materials for curation and serializes on one Host; it does not interpret curation-session exit as review of results.

- A manager organizes Issues, necessary branches, dependencies, and assignments based on the actual question, and decides follow-up work using existing contributions; no fixed tree or role sequence is required. If an experimental task must follow advice a scientist has saved in IM, explicitly identify that advice or its exact reference and explain the relationship. Leave open questions and handoff entries. Claiming only records who claimed; task completion and scientific judgments depend on actual materials and evidence.
- Roles may read, claim, and briefly reply to tasks or communicate directly using ordinary Board messages. These services remain usable without a trigger.
- Experimenters can come from the project or an external system. Record inputs, methods, conditions, results, failures, and open questions so findings and sources can later be curated. Pre-splitting into Evidence is unnecessary; submit failures, partial materials, or original references to Inbox, or contribute directly within authorization. Originals are read by the actual project; registering a reference does not mean the original was verified.
- Curators help admit Inbox submissions and other existing materials explicitly assigned to them. When possible, associate Inbox contributions with the actual packet and source text; use `curate_field_item` to admit contributions with locatable text linked to the packet. With appropriate tools and authorization, split admitted Evidence when needed while preserving meaning, conditions, sources, and explicit relations; retain gaps when information is missing. For justified corrections, preserve exact sources for the correction and old claim. If necessary, record an independently challengeable erroneous claim from old material and explicitly refute it with the correction using `refutes`. Check actually affected downstream items: use `depends_on` only for truly necessary premises. Split mixed content as needed and judge affected relations individually; unselected relations remain unchanged. Retain gaps if basis or impact is unknown; do not invent dependencies. For example, an old report misstated a sample unit and an old judgment truly depended on it. Save the sourced correction and erroneous claim, make the correction refute the claim, and make the old judgment depend on that claim, propagating the effect to its downstream. Do not add this dependency to content sharing the source but not depending on the error. Curators do not by default perform independent data audits or decide scientific correctness.
- Conclusion writers read actual Evidence and relations, organizing the current conclusion, counterexamples, applicability, and gaps. When summarizing a parent Issue, examine child conclusions and currentness; missing, stale, or unreadable child conclusions are gaps, not current conclusions. Inspect child Evidence and relations as needed and select what actually supports the conclusion. State limitations when material is insufficient; do not wait for every child Issue to have a conclusion. Fill any structured conclusion template. Do not automatically wait for curator review or assume scientific planning or acceptance duties.
- Scientists assess direction from existing material when the project lacks a clear next step or needs scientific judgment and guidance, save grounded contributions, and answer the original request. After receiving a human research question and saving guidance, explicitly hand off via Board to the manager with exact references for follow-up; an answer alone does not automatically activate the manager. Other matters needing managerial decisions can also be handed off. Not every result must pass through a scientist.
- All roles save actual results, conditions, limitations, and exact original references usable by later sessions; relate necessary bases and contributions according to their meaning. Each project supplies original storage, reference creation, and reading. Record a gap if capabilities are missing; an input reference cannot substitute for a result reference.
- IM's Issues, Evidence, relations, and conclusions preserve questions, contributions, and bases for judgments; Inbox receives materials, Queue holds tasks, and Board stores communications and explicit requests. Later participants read as needed; saving or sending a message is not proof of completion.
- Multiple contributions and explicit selection of another Issue are permitted within actual authorization; a contribution to a new location is a new action. When an original action's result is unknown, preserve its target, body, and identity and replay with recovery tools, not a new identity that duplicates the submission.

Users may configure ordinary Python scripts to discover sources read-only and request Host sessions; scripts, Hosts, and services may use different addresses. Arrival of an ordinary message or Inbox material does not itself change business state. See [IM](../../orchestration/IM_TOOLS.md), [Queue](../../orchestration/QUEUE_TOOLS.md), [Board](../../orchestration/BOARD_TOOLS.md), [Host](../../orchestration/HOST_TOOLS.md), and [Python trigger](../../orchestration/PYTHON_TRIGGER.md).

## Catalog responsibility summaries

Host `role_profiles` must be given finite `catalog` metadata by the project; `responsibility` is the summary returned to managers, not automatically generated from a role prompt. These examples can be adjusted to actual project capabilities and authorization; catalog visibility grants neither launch nor domain permissions.

| Role | Catalog responsibility summary |
| --- | --- |
| Manager | Organize work around questions, choose next steps based on contributions, and leave a continuation entry. |
| Experimenter | Perform actual exploration; save results, conditions, sources, and open questions. |
| Curator | Curate Inbox submissions and other explicitly assigned material into independently challengeable items, preserving provenance, relations, and gaps; no default independent audit or scientific adjudication. |
| Conclusion writer | On an explicit Board request, organize an Issue's current conclusion, scope, and gaps from Evidence and relations; do not wait for curator review by default. |
| Scientist | Judge research directions from materials, provide guidance and save its basis; hand off to the manager when further arrangement is needed. |

Each profile also supplies name, purpose, model description, and `queue_consumer`; a role can have multiple profiles. Only experimenter profiles that can actually consume Queue are marked true. Descriptions must match prompts, tools, and actual authorization; there is no automatic injection or global role default.

## Assembling role instructions

Task instructions, Host session `prompt`, Host catalog `catalog.responsibility`, and each MCP's tool instructions have distinct purposes. Host `prompt` explains the purpose of this activation; the catalog helps authorized principals choose resources; MCP explains tool use. Catalog text is not generated from the prompt. The trusted host configures them separately; this document is not automatically injected into sessions. External experimenters do not pass through this Host and do not receive its role prompt, but may use project-provided MCP instructions. Whether module Server Instructions reach the model depends on the client and cannot be inferred from successful initialize.

An assemblable five-role Host prompt and catalog example is [host_role_guidance.json](../../orchestration/examples/host_role_guidance.json). It is a `role_profiles` fragment: the project must still provide actual `model_profile`, `mcp`, configuration purpose, and model description; it is not a complete launch-ready Host configuration. The example accompanies a trigger script that activates curators on Inbox submissions, so a manager need not dispatch each one. Short instructions with the same boundaries follow:

- **Manager:** Organize necessary Issues, resources, and assignments, deciding follow-up from existing records. If an experimental task must follow advice saved by a scientist in IM, identify the advice or exact reference and explain the relation. Inbox submissions activate curators in the example; individual dispatch is unnecessary. When materials suffice for a summary or new evidence requires reworking the current conclusion, proactively use Board to request the conclusion writer for the actual Issue. Retain gaps when material is insufficient; do not assume dependencies are already met or treat curator review as a prerequisite for every contribution or conclusion.
- **Internal experimenter:** Conduct the assigned exploration, retaining results, conditions, sources, and open questions for continuation; the project can adjust according to work. External experimenters do not need this role instruction.
- **Curator:** Curate existing material, splitting Evidence into independently challengeable, revisable, or reusable content. Link Inbox contributions where possible to the actual packet and source text; `curate_field_item` can link locatable text. Preserve meaning, conditions, sources, explicit relations, and gaps. For justified corrections retain exact provenance for both correction and old claim; if needed, record the independently challengeable erroneous claim and explicitly refute it with the correction. Check actually affected downstream content and use `depends_on` only for genuinely necessary premises. Split mixed content as needed, judge each affected relationship, and leave unselected relations unchanged. Preserve uncertainty and do not invent dependencies. For example, if an old report misstated sample units and an old judgment actually required that unit, save sourced correction and erroneous claim, make correction refute claim, and make judgment depend on claim, so the impact propagates. Do not create this dependency for merely co-sourced content that does not depend on the error. No independent audit or scientific adjudication is assumed by default.
- **Conclusion writer:** Organize current conclusions, counterexamples, scope, and gaps from actual Evidence and relations, filling actual conclusion rules. When summarizing a parent, check child conclusions and currentness and report missing, stale, or inaccessible child conclusions as gaps rather than current. Inspect child Evidence as needed, select actual supporting basis, and state limitations if insufficient; do not wait for every child to conclude. Do not default to waiting for curator review or take on new scientific planning or acceptance.
- **Scientist:** When scientific direction or guidance is needed, read materials, propose grounded choices, questions, and limitations, save contributions with project tools, and answer the original request. After receiving a human research question and saving guidance, explicitly hand off through Board to the manager with exact references; the answer alone does not activate the manager. Other matters needing managerial decisions can also be handed off. No routine review of every result is assumed.

Roles may use a shared workspace for temporary files. Each project defines archiving timing, references, and reading; when originals must be saved, query the target project description and use host-bound project capabilities. A workspace path does not automatically promise archiving or versioning, and a new contract cannot rewrite references or fixed descriptions for existing contributions. `inspect_issue` exposes current `conclusion_rule`; the conclusion writer uses it to fill `save_working_conclusion` `structured_outputs`. The type snapshot still holds the original default, not necessarily the later current rule.

These are adjustable role profiles, not a fixed role chain. Role descriptions are not automatically assembled and do not grant permissions; projects must configure actual Host profiles and provide required tools. Original-access tools and IM contract queries also require actual host binding.

`verification_level=declared` means a source is declared, not proven verified, incorrect, or categorically unusable. `quality_status=unknown` means quality is unknown, not invalid or requiring prior curator review. Judge according to actual content, relations, refutations, and rules and retain unverified limitations; the system's evidence state does not certify scientific correctness. `questionable` and `unusable_for_purpose` are different quality states; actual eligibility remains checked by IM.

Queue keeps tasks and replies, Board communications and explicit requests, and Inbox/IM materials, contributions, and bases. Use each as needed; no call order is mandated. See [Host](../../orchestration/HOST_TOOLS.md) for how Host prompts enter session input and adapter requirements. Whether module Server Instructions reach the model on tool discovery remains client-dependent.

## Organizing Issues

Authorized participants can use `create_issue` from an IM profile to create a question with a new ID, type, and title. Supply `parent_issue_id` for a child, omit it for a root. Later sessions can use `inspect_issue` and `list_child_issues` to read the structure. The host must explicitly enable these tools and IM credentials must have `issue.write`; role name and default Issue grant no permission. Recover an unknown result as the original delivery rather than creating another action.

Use `list_issue_types` before creation to see default conclusion rules. An authorized participant can use `set_conclusion_rule` to set a complete new rule on an existing Issue when different fields are needed; `read_conclusion_rule` reads current or historical revisions. New rules constrain later conclusions; old conclusions retain their prior rules, and `inspect_issue` separately compares an old conclusion with the current rule. After a write conflict, read the latest rule and make a new decision; recover an unknown outcome using `recover_delivery`.

An Issue is a work focus, not an authorization list for Queue, Board, or Host. A principal already permitted to publish to Queue can directly use a new child Issue as a task focus. Ordinary Board messages can be queried by one Issue, by subtree through a configured IM connection, or across all Issues; subtree continuation uses returned `next_read` and an empty page can still have a next page. Explicit requests remain governed by actual recipient rules; IM independently checks its domain permissions.
