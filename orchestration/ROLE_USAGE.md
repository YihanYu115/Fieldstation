# 岗位用法

Queue 发布者选择一份实验员配置；先使用获准的 Host 目录查看该 Host 的职责和配置选项。目录可见性不授予启动或 IM 权限，具体目标 Host 在领取前独立核验。其他岗位仍可由可信脚本结合 Board 或 Inbox 激活。

这些工具是按需使用的能力，不是每轮必须执行的顺序。实际权限由服务和宿主绑定决定。 示例项目可把新研究问题直接交给科学家；科学家将指导交接给经理安排工作。示例调度在有待整理 Inbox 时优先选择入件，单 Host 串行；它不把整理会话退出当成成果已审核。

- 经理根据实际问题组织 Issue、必要的分支、依赖和分工，并结合已有贡献判断后续工作；不要求固定树或岗位顺序。实验待办需要依照科学家已在 IM 保存的建议时，明确指出该建议或其准确引用，说明任务与建议的关系；留下未决问题和接续入口。领取只是记录谁领取，任务完成与科学判断由实际材料和证据判断。
- 岗位可读取待办、领取并简短回复；也可直接使用 Board 普通消息沟通。没有触发器时仍可使用这些服务。
- 实验员可以来自本项目或外部系统；按实际工作记录输入、方法、条件、结果、失败与未决问题，使不同发现及其来源可供后续整理。无需预先拆成 Evidence；失败、部分材料或原件引用可直接提交 Inbox，也可在授权内直接贡献。原件由项目实际读取，登记引用不等于已验证原件。
- 整理员协助将 Inbox 入件及其他实际委托的已有材料规范入账；来自 Inbox 的贡献尽量与实际 packet 和来源原文关联；可用 curate_field_item 将可定位原文的贡献与 packet 关联入账。有相应工具和授权时，可按需拆分已入账 Evidence，保留原意、条件、来源和明确关系，缺信息时保留缺口。遇到有依据的更正时，保留更正及旧主张的准确来源；需要时从旧材料补录可独立质疑的实际错误主张，用更正通过 refutes 明确反驳它。检查实际受影响的下游，只有确为必要前提才建立 depends_on；混合内容可按需拆分，并逐条判断受影响的关系，未选择的关系保持原状。依据或影响不明时保留缺口，不虚构依赖。例如：旧报告把样本单位写错，旧判断确实以该单位为必要依据。保存有来源的更正与旧错误主张，使更正 refutes 旧主张；从旧判断向旧主张建立 depends_on，使更正的影响沿旧判断及其下游传播。仅与错误同源但不依赖它的内容不建立此依赖。不默认承担独立数据审计或科学正确性裁决。
- 结论员阅读 Issue 中实际 Evidence 和关系，整理当前结论、反例、适用范围和缺口；汇总父 Issue 时查看相关子 Issue 的已有结论及其当前性；子结论缺失、过期或不可读取时说明缺口，不把它当作当前结论。按需查看子 Issue 的 Evidence 和关系，选择实际支持结论正文的依据；材料不足时明确限制，不必等待每个子 Issue 先形成结论。若 Issue 有结构化结论模板，依据材料填写。不默认等待整理员审核，也不自动承担科学规划或验收。
- 科学家在项目缺少明确下一步或工作告一段落、需要科学判断和指导时，结合已有材料评估方向，保存有依据的实际贡献并答复原请求；收到人类研究问题并保存指导后，通过 Board 向经理明确交接并附准确引用，请其安排后续工作；答复本身不会自动激活经理。其他情况需要经理判断或安排后续工作时也可交接。不要求每份成果都经过科学家。
- 各岗位保存实际成果、条件、限制和可供后续会话使用的准确原件引用，并按实际含义关联必要依据或已有贡献。原件的保存、引用生成与读取由具体项目提供；缺少能力时记录缺口，不用输入引用冒充成果引用。
- IM 的 Issue、Evidence、关系和结论保留问题、贡献及判断依据；Inbox 可先收集材料，Queue 留下待办，Board 留下交流与明确请求。后续参与者按需读取这些记录接续工作，不把保存或消息当作完成证明。
- 在已有权限内可多次贡献，也可明确选择其他 Issue；新位置的新贡献是新动作。原动作结果未知时保留原目标、正文和身份并用恢复工具重放，不换身份制造重复提交。

用户可配置普通 Python 脚本只读监听来源并请求 Host 启动会话；脚本、Host 和服务可使用不同地址。普通消息和 Inbox 到达本身不改变业务状态。工具参数与限制见 [IM](IM_TOOLS.md)、[Queue](QUEUE_TOOLS.md)、[Board](BOARD_TOOLS.md)、[Host](HOST_TOOLS.md) 和 [Python 触发器](PYTHON_TRIGGER.md)。

## 目录中的职责简介

Host 的 `role_profiles` 必须由项目提供有限的 `catalog` 元数据，`responsibility` 是目录返回给经理的职责简介，不从岗位 prompt 自动生成。以下是示例，可按项目实际授权和能力修改；目录可见不授予启动或领域权限：

| 岗位 | 目录职责简介 |
| --- | --- |
| 经理 | 根据问题组织工作，结合已有贡献判断下一步，留下接续入口。 |
| 实验员 | 执行实际探索，保存成果、条件、来源和未决问题。 |
| 整理员 | 整理 Inbox 入件及其他实际委托的已有材料，按可独立质疑的内容规范入账，保留来源、关系与缺口；不默认做独立审计或科学裁决。 |
| 结论员 | 应 Board 明确请求，根据 Evidence 和关系整理 Issue 当前结论、范围与缺口；不默认等待整理员审核。 |
| 科学家 | 依据材料判断研究方向、提供指导并保存依据；需要后续安排时向经理交接。 |

各配置还提供名称、用途、模型说明与 `queue_consumer` 标记；同岗位可以有多个配置。只有实际可消费 Queue 的实验员配置标记为 true。介绍须与对应 prompt、工具及实际授权一致；不存在自动注入或岗位全局默认。

## 岗位说明的装配

任务说明、Host 的会话 `prompt`、Host 目录的 `catalog.responsibility` 和各 MCP 的工具说明分别承担不同作用。Host 的 `prompt` 说明本次唤醒参与者的用途，目录帮助有权限的主体选择资源，MCP 说明工具怎么用；目录不会从 prompt 自动生成。可信宿主分别配置它们，本文件不会自动注入会话。外部实验员不经过本 Host，不接收 Host 岗位 prompt；它仍可通过项目提供的 MCP 使用说明理解工具。模块 Server Instructions 是否实际交给模型取决于客户端，不能由 initialize 成功推断。

可装配的五岗 Host prompt 与目录示例见 [host_role_guidance.json](examples/host_role_guidance.json)：它是 `role_profiles` 的片段，项目还须填写实际 `model_profile`、`mcp`、配置用途和模型说明，不是可直接启动的完整 Host 配置。示例与 Inbox 入件激活整理员的触发脚本配套；经理不需要为每份入件另行派发。以下是同一职责边界的简短说明：

- 经理：根据问题组织必要的 Issue、资源和分工，结合已有记录决定后续工作；实验待办需要依照科学家已在 IM 保存的建议时，明确指出该建议或其准确引用，说明任务与建议的关系。Inbox 入件会激活整理员，不需要为每份入件另行派发。当已有材料足以总结，或需结合新证据重新整理当前结论时，主动通过 Board 请求结论员处理实际 Issue。材料不足时保留缺口，不提前假定依赖已满足；不把整理员审核当成所有成果或结论的前置条件。
- 内部实验员：受委托开展本次实际探索，保留结果、条件、来源和未决问题，便于接续；项目可根据实际工作调整。外部实验员不需要此岗位说明。
- 整理员：整理已有材料，按可独立质疑、修订或复用的内容拆分 Evidence；来自 Inbox 的贡献尽量与实际 packet 和来源原文关联；可用 curate_field_item 将可定位原文的贡献与 packet 关联入账。保留原意、条件、来源、明确关系及缺口；遇到有依据的更正时，保留更正及旧主张的准确来源；需要时从旧材料补录可独立质疑的实际错误主张，用更正通过 refutes 明确反驳它。检查实际受影响的下游，只有确为必要前提才建立 depends_on；混合内容可按需拆分，并逐条判断受影响的关系，未选择的关系保持原状。依据或影响不明时保留缺口，不虚构依赖。例如：旧报告把样本单位写错，旧判断确实以该单位为必要依据。保存有来源的更正与旧错误主张，使更正 refutes 旧主张；从旧判断向旧主张建立 depends_on，使更正的影响沿旧判断及其下游传播。仅与错误同源但不依赖它的内容不建立此依赖。不默认承担独立数据审计或科学裁决。
- 结论员：根据 Issue 的实际 Evidence 和关系整理当前结论、反例、适用范围和缺口，按实际结论规则填写；汇总父 Issue 时查看相关子 Issue 的已有结论及其当前性；子结论缺失、过期或不可读取时说明缺口，不把它当作当前结论。按需查看子 Issue 的 Evidence 和关系，选择实际支持结论正文的依据；材料不足时明确限制，不必等待每个子 Issue 先形成结论。不默认等待整理员审核，也不承担新的科学规划或验收。
- 科学家：在需要判断研究方向或指导时，阅读相关材料，提出有依据的选择、问题和局限，使用项目工具保存实际贡献并答复原请求；收到人类研究问题并保存指导后，通过 Board 向经理明确交接并附准确引用，请其安排后续工作；答复本身不会自动激活经理。其他情况需要经理判断或安排后续工作时也可交接。不承担每项成果的例行审核。

岗位可使用共享工作区处理临时文件。项目自行约定留档时机、引用和读取规则；需要保存原件时查询目标项目说明并使用宿主绑定的项目能力。工作区路径不自动具备留档或版本保证，已有贡献的引用和固定说明也不能因新契约而改写。`inspect_issue` 的 `conclusion_rule` 给出当前结论规则；结论员依此填写 `save_working_conclusion` 的 `structured_outputs`。类型快照仍保留创建时的原始默认规则，不代表后来修改后的当前规则。

这些是可调整的岗位配置，不是固定岗位链。角色说明不会自动装配或授予权限，项目须在实际 Host profile 中配置并提供所需工具；项目原件工具与 IM 契约查询也须由宿主实际绑定。

`verification_level=declared` 表示来源处于声明层级，不证明已核验，也不等于错误或一律不能使用；`quality_status=unknown` 表示质量未知，不等于无效或必须先经整理员审核。结合实际内容、关系、反驳和适用规则判断，并保留未核验的限制；系统依据状态不是科学正确性认证。`questionable` 和 `unusable_for_purpose` 是不同的质量状态，实际资格仍由 IM 检查。

Queue 留待办及回复，Board 留交流和明确请求，Inbox/IM 保存材料、贡献和依据；各自按实际需要使用，不规定调用顺序。Host 中的提示词进入会话输入的路径及适配器要求见 [Host](HOST_TOOLS.md)；模块 Server Instructions 在工具发现时是否交付仍由实际客户端决定。

## 组织 Issue

获得实际授权的参与者可用 IM profile 的 `create_issue` 创建问题，填写新的 ID、类型和标题；创建子问题时填写 `parent_issue_id`，创建根问题时省略。后续会话可用 `inspect_issue` 和 `list_child_issues` 读取结构。宿主须明确启用这些工具，IM 凭据须具有 `issue.write`；岗位名称和默认 Issue 不授予权限。结果未知时恢复原交付，不另建动作。

创建前可用 `list_issue_types` 查看类型的默认结论规则。需要不同字段时，有授权的参与者可用 `set_conclusion_rule` 为已有 Issue 设置完整的新规则，`read_conclusion_rule` 可读当前或历史版本。新规则约束之后提交的结论；旧结论保留当时规则，`inspect_issue` 单独显示旧结论与当前规则的比较。写入冲突时先读取最新规则再作新的业务决定；结果未知时使用 `recover_delivery` 恢复原动作。

Issue 是实际工作焦点，不是 Queue、Board 或 Host 的权限名单。已有 Queue 发布权限的主体可直接将新子 Issue 作为待办焦点。Board 的普通留言可查询单个 Issue、通过已配置的 IM 连接查询子树，或查询全部 Issue；子树续页使用返回的 `next_read`，即使本页为空也可能还有下一页。明确请求仍受实际收件人规则约束，IM 自身的领域权限仍由 IM 检查。
